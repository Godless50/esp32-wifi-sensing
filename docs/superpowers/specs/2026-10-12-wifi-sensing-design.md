# Wi-Fi Sensing на ESP32-S3 — спецификация

Дата: 2026-10-12. Статус: на согласовании.

## 1. Цель и границы

**Цель.** Одна плата ESP32-S3 N16R8 по CSI одной радиолинии (плата ↔ узел mesh `HomeNet`, канал 1)
распознаёт: присутствие человека, интенсивность движения, комнату/зону, позу, примерные координаты.
Модель обучается на сервере, исполняется на плате, дообучается сервером по исправлениям из UI
и доставляется на плату по OTA. UI показывает 3D-сцену квартиры и человека в ней.

**Что сказал пользователь:**
- одна радиолиния; 2.4 ГГц сеть работает на канале 1;
- модель обязательна; обучение на сервере, затем сервер дообучает модель и обновляет её на плате;
- в UI — 3D-пространство со стенами, объектами, людьми;
- рисовать план вручную не будет, готов пройтись по комнатам; телефон — Android с ARCore.

**Допущения (не подтверждены пользователем):**
- во время записи обучающих сессий в наблюдаемой зоне находится только пользователь (питомцы/другие люди портят разметку);
- плату можно переставить в 3–6 м от выбранного узла mesh (сейчас −29 dBm, ~1 м — плохо для чувствительности);
- сервер и телефон в одной локальной сети; доступ извне не нужен;
- порты 8443/tcp и 5005/udp на сервере свободны (проверено: из нужных занят только 80/tcp).

**Вне границ:** несколько плат/радиолиний; трекинг нескольких людей; восстановление геометрии
(стен, предметов) из Wi-Fi; съёмка с iPhone; доступ из интернета; дообучение весов на самой плате.

**Физические ограничения (зафиксированы пробой 2026-10-12, `probe-scan/scan.log`):** beacon-кадры узлов
mesh CSI не дают (вероятно, 802.11b DSSS), поэтому источник CSI — только активный ping через связанный узел.
Стены и предметы в 3D-сцене — разметка пользователя, а не результат распознавания.
Точность позиции ограничена различимостью зон для одной линии; измеряется, а не обещается.

## 2. Критерии успеха

| # | Критерий | Как проверяется |
|---|---|---|
| S1 | CSI ≥ 80 кадров/с устойчиво 10 мин | телеметрия платы, скрипт `hil_csi_rate.sh` |
| S2 | Инференс на плате ≤ 100 мс на окно, модель ≤ 200 КБ | лог платы, размер артефакта |
| S3 | Совпадение классов плата/сервер на одних окнах ≥ 99 % | тест паритета |
| S4 | Задержка «событие → UI» ≤ 1 с | метки времени в WS-сообщении |
| S5 | Отчёт качества: accuracy/macro-F1, матрица ошибок по каждой голове на отложенной сессии | страница `/model` |
| S6 | Новая модель уходит на плату, только если macro-F1 ≥ текущей − 0.01 | тест гейта деплоя |

Целевое (не гарантируемое) значение: «пусто/есть человек» ≥ 95 % на отложенной сессии.

## 3. Архитектура

```
[ESP32-S3] --UDP 5005: CSI 100 Гц + предсказания 4 Гц--> [Сервер, docker compose]
   ping 100 Гц на шлюз (источник CSI)                     ├ api: приём UDP, REST, WebSocket, статика UI
   HTTPS 8443: конфиг, модель, прошивка (OTA) <---------- ├ trainer: обучение/экспорт int8 TFLite
                                                          └ caddy: TLS (mkcert CA) на 8443
[Android Chrome, WebXR] --WSS 8443: поза 30 Гц, углы, метки--> api
```

Выбран вариант A: ESP-IDF 5.4 (образ `espressif/idf:release-v5.4`) + TFLite Micro
(`espressif/esp-tflite-micro`), сервер Python 3.12 + FastAPI + TensorFlow/Keras (CPU).

## 4. Прошивка

### 4.1 Задачи FreeRTOS
| Задача | Назначение |
|---|---|
| `wifi_mgr` | STA к SSID с жёстким BSSID, `WIFI_PS_NONE`, переподключение 1→30 с экспоненциально |
| `ping_gen` | ICMP echo на шлюз с частотой `ping_hz` (по умолчанию 100) |
| `csi_cb` | колбэк CSI: фильтр по MAC узла, копия в кольцевой буфер (PSRAM, 4 с) |
| `uplink` | пачки по 10 кадров → UDP на сервер |
| `infer` | каждые 250 мс: признаки окна → TFLite Micro → результат в UDP |
| `ctrl` | раз в 30 с HTTPS-опрос конфига и версий модели/прошивки; OTA |
| `console` | `esp_console` по USB: `wifi set`, `server set`, `key set`, `status`, `reboot` |

### 4.2 Источник CSI
- `wifi_csi_config_t`: `lltf_en=1, htltf_en=1, stbc_htltf2_en=0, ltf_merge_en=0, channel_filter_en=0`.
- Принимаются кадры только от BSSID связанного узла.
- Настройка `csi_source` = `ht` (по умолчанию: только HT-кадры, используется HT-LTF, K=56 ненулевых
  поднесущих) или `lltf` (все OFDM-кадры, L-LTF, K=52). Индексы поднесущих задаёт `shared/subcarriers.json`,
  из него генерируются C-заголовок и Python-константы.
- Отброшенные кадры считаются и уходят в телеметрию; если доля > 20 % — предупреждение в UI.
- Признак поднесущей: амплитуда `|H| = sqrt(I² + Q²)`. Фаза не используется (без синхронизации
  она шумовая на одной антенне).

### 4.3 Формат UDP (little-endian)
Заголовок пачки: `magic "WSN1"` (4) · `ver u8` · `type u8` (1=CSI, 2=PRED, 3=TELEM) · `device_id u8[6]` (MAC)
· `seq u32` · `n u8` · … полезная нагрузка … · `hmac u8[16]` (усечённый HMAC-SHA256 по всему предшествующему).

CSI-кадр: `t_us u64` (esp_timer) · `rssi i8` · `noise i8` · `sig_mode u8` · `cwb u8` · `len u16` · `data i8[len]`.

PRED: `t_us u64` · `model_ver u32` · `p_occ f32` · `motion f32` · `zone_n u8` · `p_zone f32[zone_n]`
· `pose_n u8` · `p_pose f32[pose_n]` · `x f32` · `y f32` · `infer_us u32`.

TELEM (раз в 1 с): `csi_hz f32` · `drop_ratio f32` · `rssi_avg i8` · `heap_free u32` · `psram_free u32`
· `uptime_s u32` · `fw_ver u32` · `model_ver u32` · `wifi_state u8`.

### 4.4 Разметка флеша (16 МБ)
| Раздел | Размер |
|---|---|
| nvs | 24 КБ |
| otadata | 8 КБ |
| phy_init | 4 КБ |
| ota_0 / ota_1 | 3 МБ / 3 МБ |
| model_a / model_b | 1 МБ / 1 МБ |
| остаток | резерв |

Модель: заголовок (`magic`, `version`, `sha256`, `len`, метаданные JSON: K, списки зон/поз, константы
нормализации, параметры окна) + `.tflite`. Загрузка в неактивный слот → проверка sha256 → переключение
указателя в NVS → инициализация интерпретатора; при ошибке остаётся старый слот.
Прошивка: `esp_https_ota` с откатом (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`); новая прошивка
подтверждается после 60 с здоровой работы (CSI ≥ 50 Гц), иначе откат.

### 4.5 Безопасность
- HTTPS к серверу с закреплённым корневым сертификатом mkcert (встроен в прошивку).
- UDP-пачки подписываются HMAC (см. 4.3), ключ устройства в NVS задаётся консольной командой;
  сервер отбрасывает пакеты с неверной подписью или повтором `seq`.
- Пароль Wi-Fi и ключ — только в NVS и локальном `secrets.env` (в `.gitignore`).

### 4.6 Ошибки
- Нет связи с узлом: инференс на паузе, `wifi_state` в телеметрии, повторные попытки; на другой BSSID
  плата не переключается (модель привязана к радиолинии).
- CSI < 20 Гц 10 с подряд: перезапуск `ping_gen`, событие в телеметрии.
- Сервер недоступен: инференс продолжается локально, OTA-опрос с backoff до 5 мин.
- Task watchdog на всех задачах.

## 5. Признаки и модель (одинаковые в C и Python)

- Окно 1.28 с → 64 временных бина по 20 мс; бин = среднее кадров; пустые бины — линейная интерполяция;
  окно отбрасывается, если пустых бинов > 25 %.
- Вход 64 × K × 2: канал 1 — `A − mean_t(A)` (динамика); канал 2 — `mean_t(A)`, повторённое по времени
  (статика, нужна для зоны и состояния предметов). Оба нормируются константами из метаданных модели.
- Квантование int8 входа по параметрам из `.tflite`.
- Сеть: Conv1D(2K→64, k5) → Conv1D(64, k5, s2) → Conv1D(64, k3, s2) → GAP → Dense(64) → головы:
  `occ` (2, softmax), `motion` (1, sigmoid), `zone` (N комнат, softmax), `pose` (4: стоит/сидит/лежит/идёт),
  `xy` (2, линейная, метры). Ориентир — ~60 тыс. параметров.
- Головы `zone/pose/xy` учитываются в loss только на окнах с `occ=1`.
- Реализация признаков: C (`features.c`) и Python (`features.py`) сверяются golden-векторами.

## 6. Сервер

### 6.1 Компоненты
- `api` (FastAPI + uvicorn): UDP-приёмник (asyncio), REST, WebSocket `/ws/live` (UI) и `/ws/capture` (телефон),
  статика UI, выдача конфига/модели/прошивки плате.
- `trainer`: задания из таблицы `jobs` (SQLite), тот же образ; TensorFlow CPU.
- `caddy`: TLS на 8443 сертификатом mkcert; CA-файл отдаётся по `https://server:8443/ca.crt`
  (первый раз — с предупреждением браузера) для установки на телефон.

### 6.2 Хранилище
- SQLite `wsn.db`: `devices`, `sessions`, `rooms`, `objects`, `models`, `jobs`, `corrections`.
- Файлы: `data/sessions/<id>/csi.bin` (сырые пачки), `pose.jsonl`, `events.jsonl` (метки, углы), `meta.json`.
- Живой поток целиком не пишется: кольцевой буфер 30 с в памяти; при исправлении из UI сохраняются
  10 с до и 5 с после. Объём записи сессии ~40 МБ/час.

### 6.3 Синхронизация времени
- CSI: отображение `t_us` платы во время сервера по минимальной задержке (min-фильтр по окну 60 с).
- Телефон: ping/pong по WS каждые 5 с, смещение часов по минимальному RTT.
- Допуск рассинхронизации ±50 мс.

### 6.4 Система координат и план
- Начало сессии: телефон у платы → «старт» (начало координат); затем у узла mesh → «роутер» (ось X).
  Все сессии приводятся к этой системе (2D-поворот + сдвиг; высота — от пола по hit-test).
- Комната: «новая комната» + имя, затем касания в углы (WebXR hit-test) → полигон.
  Запасной способ угла — «телефон приложен к стене» (берётся текущая позиция телефона).
- Предмет: касание по месту + тип (шкаф/стол/диван/кровать/дверь/другое) + габариты по умолчанию.
- Зоны: комната (голова `zone`) и координаты `xy` (голова `xy`); ячейки 1 м — только для отображения.

### 6.5 Датасет, обучение, деплой
- Окна с шагом 0.25 с. Метки: `occ=0` — из сессии «пусто» (запуск записи, пользователь уходит из квартиры
  или из зоны видимости), иначе 1; `zone`/`xy` — из позы телефона; `pose` — текущая кнопка;
  `motion` — скорость телефона, нормированная в [0, 1] (1 = ≥ 1.5 м/с).
- Разбиение по сессиям (не по окнам); последняя сессия каждого типа — отложенный тест.
- Экспорт: Keras → TFLite full-int8 с репрезентативным набором; проверка: совпадение классов int8 vs float ≥ 98 %.
- Дообучение: по кнопке или автоматически при ≥ 50 новых исправлениях; полное переобучение на всех данных.
- Гейт деплоя S6; прошедшая модель помечается активной, плата получает её при следующем опросе.
- Теневой инференс: сервер считает тот же `.tflite` по живому потоку — проверка паритета S3.

## 7. UI

| Страница | Содержимое |
|---|---|
| `/` 3D | Three.js: стены из полигонов (высота 2.6 м), предметы-кубы, маркеры платы и узла, фигура человека в позиции/позе, подсветка комнат по вероятности, индикатор движения, кнопки исправления |
| `/capture` | для телефона: WebXR immersive-ar, кнопки старт/роутер/комната/угол/предмет/поза/«пусто», статус записи и CSI-частоты |
| `/data` | сессии, длительность, разметка; исправления; запуск обучения; ход задания |
| `/model` | версии, метрики по головам, матрица ошибок, статус деплоя |
| `/device` | RSSI, CSI Гц, доля отброшенных, версии прошивки/модели, OTA |

Исправление в `/`: «сейчас пусто», «я здесь» (клик по полу), «поза …» → запись в `corrections`
вместе с окном CSI из кольцевого буфера.

## 8. Тестирование
- Прошивка: host-тесты `features.c` (gcc) против golden-векторов из `features.py`; парсер заголовка модели.
- HIL-скрипты: прошивка → 30 с измерения CSI Гц ≥ 80, время инференса, проверка OTA-отката.
- Сервер (pytest): парсер UDP и HMAC, синхронизация времени, полигоны/зоны, сборка датасета на синтетике,
  обучение на синтетике до заданной точности, int8 vs float, гейт деплоя.
- UI: Playwright smoke для страниц (без WebXR — поза подаётся тестовым WS-клиентом).
- E2E: воспроизведение записанной сессии в UDP-порт → предсказания в WS.

## 10. Риски
- **Диск сервера 98 %** (10 ГБ свободно): образ TF ~2–3 ГБ плюс уже имеющийся образ IDF. Нужно освободить
  10–20 ГБ до этапа обучения.
- Различимость зон по одной линии неизвестна — может оказаться на уровне «комната», а не «часть комнаты».
- Перестановка мебели, смена узла mesh или канала ломают модель → переобучение.
- Mesh может сам сменить канал или отключить узел: плата сообщит, распознавание остановится.
- WebXR hit-test по стенам при плохом освещении нестабилен; запасной путь описан в 6.4.
- Принимает ли Chrome WebXR при самоподписанном сертификате без установки CA — не проверено; закладываем mkcert.
